# M2 后端 · 技术开发文档

- 日期：2026-10-03
- 分支：`feat/m2-backend`（从已验收基线 `dev/ifplay-m0@8d97218` 分叉）
- 目录：`apps/ifplay-backend/`
- 范围：受控 GameBundle 主轨完整产品闭环（含内容修复、自然语言修改、统一费用账本、澄清上限、方案卡补全、版本上限）；不接入 OpenGame 自由代码生成。

> 第一阶段：打通 `想法→会话→澄清→方案卡→确认→生成→校验→版本→恢复` 纵向闭环 + 单进程持久化长任务。
> 第二阶段（本阶段）：补齐受控 GameBundle 主轨的产品闭环——统一费用账本、澄清上限、方案卡补全与历史、内容修复、自然语言修改、版本数量上限。

## 1. 目标

实现 M2 创作闭环后端：输入想法 → 创作会话 → 澄清问答（有上限）→ 方案卡（可修改/重推）→ 确认 → 生成任务（含修复）→ 校验 → 保存版本 → 自然语言修改 → 版本恢复。

## 2. 架构

- FastAPI + SQLite（SQLAlchemy 2）。`/api/v1` 前缀，统一错误 `{"error":{"code","message"}}`。
- 状态机在 `app/state.py`：generation 与 modification 两套显式转换，非法转换返回 409。
- Provider 统一接口（`app/providers/base.py`），供应商无关；当前 `deterministic-test`（`is_real=False`）。
- 双轨预留：`GameBundleTrack`（本阶段唯一可执行）与 `IsolatedCodeTrack`（返回「尚未接入」，不执行代码）。
- 统一费用账本（`app/billing.py`）：所有模型调用经 `provider_call_with_billing` 统一预检、计费、失败留痕、会话聚合。

## 3. 数据对象

`CreationSession`、`Clarification`、`PlanCard`（含补充字段 + `is_current` 历史标记）、`GenerationTask`（`kind` = generation/modification，一会话可多个修改任务）、`GameVersion`（含 `parent_version_id` 与 `is_archived`）、`UsageLedger`（`session_id` + `purpose` + `error_code`）、`ValidationResult`。

数据库变更向后兼容：`app/db.py::_migrate` 启动时对旧库补列并回填，不删除、不重建、不丢数据。

## 4. 任务状态机（持久化长任务）

generation：`draft → clarifying → plan_ready → confirmed → queued → generating → validating → playable`。
modification：`queued → applying → validating → succeeded`。

- `queued`：创建任务只持久化入队即返回（HTTP 202），不等待结束。
- `interrupted`：`generating/applying/validating` 在服务重启时变为 `interrupted`（generation=`generation_interrupted` / modification=`modification_interrupted`），不自动重试，仅可显式 resume 重新入队。
- 终态：generation=`playable/failed`；modification=`succeeded/failed`。

### 4.1 后台工作器与恢复

- 单进程后台线程（`app/worker.py`）从 SQLite 领取 `queued` 任务；条件 UPDATE 原子领取，按 `kind` 进入 `generating` 或 `applying`。
- 启动（lifespan）：初始化 DB → 迁移 → 恢复检查（进行中→interrupted，queued 保留）→ 启动工作器。
- 显式恢复 `POST /tasks/{id}/resume`、`POST /modifications/{id}/resume`（idempotency_key + confirm_retry=true，幂等，保留旧用量）。

## 5. 统一费用账本（`app/billing.py`）

- 澄清 / 方案 / 方案修改 / 重推 / 生成 / 内容修复 / 自然语言修改 全部进入同一会话账本（按 `session_id` 聚合，跨任务累计）。
- 每次调用记录 provider/model/version/输入 Token/输出 Token/耗时/费用/用途/状态。
- usage 缺失立即失败（`missing_usage`，不按 0 元）。
- 每次调用前最坏成本预检；实际用量结算在调用后。
- 失败调用保存可审计状态（`status=failed` + `error_code`），不含提示词全文。
- 累计费用只累加、不清零（跨中断/恢复/修改）。

## 6. GameBundle 契约（共享，不手写漂移契约）

运行时权威 Zod schema 经 `npm run export:contract` 生成 `apps/ifplay-m0/contract/gamebundle-contract.json`，后端消费并做五类检查：结构（JSON Schema）、模块 config、白名单玩法、引用完整性、安全字段（禁 eval/Function/script/HTML）。

## 7. 内容修复

- 首次生成后运行完整五类校验；失败时把机器可读校验错误交给 Provider 修复。
- 每次修复重新执行完整校验；最多两轮（`IFPLAY_MAX_REPAIR_ROUNDS=2`，第 3 次禁止调用）。
- 每轮单独记账（purpose=repair），调用前检查剩余预算。
- 修复失败不创建可玩版本。
- 网络重试（Provider.call 内部有限重试）与内容修复严格区分，不互相伪装。

## 8. 自然语言修改（结构化补丁）

- 用户基于现有可玩版本提交修改要求，异步入队（`modification` 任务）。
- Provider 只能返回结构化补丁（`[{"op":"set","path":...,"value":...}]`），不得返回代码。
- 补丁先做允许路径检查（`app/patch.py` 白名单 + 类型/范围/代码注入约束），再应用到副本。
- 应用后执行完整契约/引用/白名单/安全校验。
- 成功创建新版本（`parent_version_id` 指向原版本）；失败不覆盖当前可玩版本。

## 9. 版本数量上限

- `IFPLAY_MAX_VERSIONS=10` 真正执行：默认只展示最近 N 个可玩版本。
- 超出部分标记 `is_archived`（不物理删除），保留审计关系。
- 归档版本不可作为修改基线（409 `version_archived`）；恢复=创建新版本。
