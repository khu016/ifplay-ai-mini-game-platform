# 第一阶段技术开发文档｜M0 规则引擎验证

> 项目：IfPlay AI 模拟器游戏平台
> 阶段：2 后端 MVP · 第一子阶段 = **M0 规则引擎验证**（不含 M1）
> 日期：2026-09-28
> 状态：待产品经理确认后开发（本阶段不写代码、不装依赖、不建数据库）

---

## 一、对产品和 M0 范围的理解

**产品**：IfPlay AI 模拟器游戏平台——用户用中文描述任意题材，经 AI 澄清与方案确认后，生成一个可直接在浏览器游玩的轻量 2D 模拟器，并支持修改、发布、分享、做同款。核心安全约束是：**AI 只生成结构化 `GameSpec` JSON，固定引擎确定性执行，不执行 AI 生成的任何代码**。

**M0 只做规则引擎验证，不接模型**：

- 固定 `GameSpec` v0.1 数据结构（基础模块：回合/时间、属性/资源、标记、条件/选项/效果、事件、结局）。
- 规则引擎：确定性解释执行 GameSpec。
- 校验器：结构校验 + 引用完整性校验。
- 自动路径模拟：多路径推进、死局检测、资源越界检测。
- 结局可达性检查：至少一个结局从初始状态可达。
- 三个手写示例 GameSpec（不用 AI 生成）。
- 最简试玩页面（浏览器直接运行，本地存档）。
- **M0 不调用真实 DeepSeek API、不产生模型费用**，全部用 mock/手写数据。

**M1（M0 验收通过后才做）**：接入 DeepSeek，完成想法输入 → AI 澄清 → 方案确认 → GameSpec 生成 → 试玩 → 自然语言修改与版本保存的闭环，仅本地/私有，不公开发布。

## 二、两种技术栈的比较与最终建议

游戏要在浏览器直接运行，规则引擎需要"确定性执行、可测试、可复用"，因此**规则引擎必须用 TypeScript**（两种方案的引擎都是 TS，差异只在后端有无与语言）。

| 维度 | 方案 A：TS 引擎 + TS 前端（+ 后续轻量后端） | 方案 B：TS 浏览器引擎 + Python/FastAPI 后端 |
| --- | --- | --- |
| 引擎确定性执行 | 单一 TS 引擎，Node 测试与浏览器跑同一份代码 | 同左（引擎仍在浏览器 TS） |
| 跨语言漂移风险 | 无（前端/测试/引擎同语言） | 引擎 TS、后端 Python，但边界清晰（引擎不进后端） |
| M0 是否需要后端 | **不需要**（无账户/无模型/无多用户，localStorage 存档即可） | 需要（为"技术栈完整"引入，违反"不引入需求未触发模块"） |
| 后端生态成熟度 | TS 后端（Hono/Fastify）够用 | Python 生态（任务队列、审核/短信 SDK）更丰富 |
| 后续接审核/短信 SDK | 可能需自写客户端 | 现成 SDK 多 |

**最终建议：M0 采用方案 A 的"无后端子集"——纯 TypeScript 单包（规则引擎 + 校验器 + 模拟器 + 最简试玩页），不引入后端、不建数据库。**

理由：
1. M0 不调用模型、无账户、无多用户，后端和数据库是"需求未触发的模块"，按核心规则卡不应引入。
2. 规则引擎是唯一权威实现，TypeScript 一份代码同时被 Vitest（Node）和浏览器复用，避免"Python 端引擎 + 浏览器 JS 引擎"双实现漂移。
3. 后续 M1 需要后端（调 DeepSeek、持久化任务/版本）时再引入，且倾向 **TS 轻量后端**（与引擎同栈、共享 GameSpec 类型定义，避免 schema 前后端漂移）；若届时审核/短信等需 Python 生态 SDK，再回退方案 B——规则引擎仍留在浏览器，Python 只做 API 与持久化，不影响已定引擎。

> SQLite 本地持久化：M1 版本/任务持久化时引入；M0 用 localStorage 存档，不建数据库。

## 三、M0 系统架构

纯前端静态站点（Vite + TypeScript），无后端、无数据库。

```text
GameSpec JSON ──▶ 校验器 ──▶ 规则引擎 ──┬─▶ 最简试玩页（浏览器运行，localStorage 存档）
                    │                   └─▶ 自动路径模拟器（Node/浏览器，带 seed）
                    └─▶ 结构/引用/语义校验
```

模块划分（全部在一个 TS 包内，Node 与浏览器共享源码）：

- `schema`：GameSpec v0.1 类型定义与示例。
- `validate`：校验器（结构、引用完整性、语义、死局静态提示）。
- `engine`：规则引擎（回合循环、条件求值、效果执行、结局判定、seedable PRNG、存档序列化）。
- `simulate`：自动路径模拟（多 seed/多策略路径、死局与越界检测、结局可达性）。
- `ui`：最简试玩页（读 GameSpec，渲染事件卡、选项、数值、结局）。
- `samples`：三个手写 GameSpec JSON。

## 四、GameSpec v0.1 模块设计

采用**版本化 JSON**（借鉴 AI Game Studio），`schemaVersion: "0.1"` 作为首版。M0 只含基础模块；P1 模块（任务/地点/关系/背包/经营）在后续切片以 v0.2/v0.3 扩展，M0 不声明、不实现，避免"声明了却不执行"。

| 实体 | 字段 | 说明 |
| --- | --- | --- |
| `metadata` | `title, description, genre, targetTurns, lang` | 标题、简介、题材标签、目标回合数、语言 |
| `clock` | `unit, total` | 回合单位（`day/week/month/turn`）与总回合数 |
| `stats` | `id, name, initial, min, max, visible` | 属性/资源：初值、上下限、可见性 |
| `flags` | `id, name` | 布尔标记（一次性事件、阶段解锁），默认 false |
| `events` | `id, title, body, condition, weight, cooldown, once, options[]` | 事件：触发条件、权重、冷却、一次性、文案、选项 |
| `endings` | `id, title, body, condition, priority` | 结局：条件、优先级、文案 |

`options[]` 每项：`text, condition?, effects[]`。`body`/`title`/`text` 均为**纯文本**，支持白名单内联变量占位（如 `{money}` 渲染为数值），不允许 HTML/脚本。

## 五、条件、效果、事件和结局的安全表达方式

全部为**白名单结构化表达式**，无任意脚本。禁止 `eval`、`Function`、`new Function`、SQL、HTML 注入；随机过程必须可传 `seed`。

**条件（Condition，递归白名单）**

```ts
type Condition =
  | { op: "flag"; flag: string; not?: boolean }
  | { op: "compare"; stat: string; cmp: ">="|"<="|">"|"<"|"=="|"!="; value: number }
  | { op: "turn"; cmp: ">="|"<="|">"|"<"|"=="; value: number }   // 当前回合数
  | { op: "all"; conditions: Condition[] }
  | { op: "any"; conditions: Condition[] };
```

**效果（Effect，白名单操作）**

```ts
type Effect =
  | { op: "set_stat"; stat: string; value: number }
  | { op: "add_stat"; stat: string; delta: number }
  | { op: "set_flag"; flag: string; value: boolean }
  | { op: "goto"; event: string }                 // 直接跳转到指定事件
  | { op: "trigger_ending"; ending: string }
  | { op: "roll"; rolls: { weight: number; effects: Effect[] }[] };  // 带 seed 的随机分支
```

**事件与结局**

```ts
type Event = {
  id: string; title: string; body: string;
  condition?: Condition;
  weight: number;              // ≥0，加权采样（0 表示仅被 goto/条件触发）
  cooldown?: number;           // 回合冷却
  once?: boolean;              // 一次性（触发后不再出现）
  options: { text: string; condition?: Condition; effects: Effect[] }[];
};
type Ending = { id: string; title: string; body: string; condition?: Condition; priority: number };
```

**确定性保证**：所有随机（事件加权采样、`roll` 分支）统一使用引擎注入的 seedable PRNG（如 mulberry32/xorshift32，纯 JS、Node 与浏览器同 seed 同结果）。同一 GameSpec + 同一 seed + 同一初始状态 → 同一路径。

## 六、规则执行流程

1. **初始化**：载入 GameSpec，按 `stats.initial` 初始化数值、`flags` 置 false、`turn=0`、生成 seed。
2. **回合循环**（每回合）：
   a. `turn += 1`；若 `turn > clock.total` → 触发"超时结局"（若有）或直接结束。
   b. **结局判定**：按 `priority` 从高到低找第一个 `condition` 满足的结局 → 命中即结束游戏并展示结局。
   c. **事件采样**：从 events 中筛出条件满足、未在冷却、未因 `once` 失效的事件，按 `weight` 用 PRNG 加权采样一个。
   d. **展示与选择**：渲染事件标题/正文/数值，列出条件满足的选项；用户选一个。
   e. **执行效果**：顺序应用该选项的 `effects[]`（`roll` 用 PRNG 选分支），数值夹紧到 `min/max`。
   f. 回到下一回合。
3. **存档**：任意时刻可序列化 `{ schemaVersion, gameSpecId, seed, turn, stats, flags, firedOnce[], cooldowns }` 到 localStorage；恢复时反序列化后继续。

## 七、校验和结局可达性方案

校验器分三层，全部确定性代码：

1. **结构校验**：字段类型、必填、枚举合法（`cmp/op/unit`）、数值合法（权重 ≥0、`min≤max`、`initial` 在界内）、ID 唯一且合法。
2. **引用完整性**：所有 `stat/flag/event/ending` 引用必须存在；`goto`/`trigger_ending` 目标存在；无悬空引用（QA-01/02）。
3. **语义/静态提示**：无有效选项的事件、永不满足的条件（静态可判时）、权重恒为 0 且无 goto 指向的事件等，给出警告。

**结局可达性**（QA-03/04）：从初始状态出发，自动跑多条路径（多 seed × 多选项策略：随机、贪心、边界值），检测：
- 是否存在至少一个结局可达（PRD QA-04 硬指标）。
- 是否存在"立即死局"（所有可触发事件耗尽、无结局可达、回合无法推进）。
- 资源是否越界（stat 超 `min/max`）。
- 是否存在不可达结局（多路径均无法命中）。
输出结构化报告，作为"成功生成"的证据之一。**模型不能以一句"测试通过"替代真实测试结果**，判定只依据工具输出。

## 八、自动测试方案

- **Vitest**（Node 环境，与浏览器共享同一引擎源码）：
  - 校验器：合法/非法用例、引用完整性、枚举与数值边界。
  - 引擎：条件求值、效果执行、`roll` 分布、权重采样、cooldown/once、结局 priority、数值夹紧。
  - 确定性：同 seed 同路径（多次运行结果一致）。
  - 模拟器：结局可达、死局检测、资源越界检测。
  - 三个手写 GameSpec 的端到端回归（跑完一轮）。
- **Playwright 浏览器冒烟**（QA-05）：首屏加载、开始游戏、选择一次、存档、恢复，无阻断错误。
- **安全断言**：源码与构建产物中不含 `eval`/`Function`/`new Function`（测试 + 人工审查）。
- M0 **不调用真实模型**，全部用 mock 数据，不产生费用。

## 十一、三个手写示例游戏（已定稿）

整体风格：互联网抽象、无厘头、适合分享传播的**原创荒诞**题材。文案可荒诞，但游戏规则必须清楚；每个选项都要让玩家理解可能影响的方向。

内容红线：不使用真实人物/公司/现成影视角色/受保护品牌形象；不照搬网络热梗，用原创荒诞设定。

引擎约束：三个游戏共用同一套 GameSpec 和规则引擎，**不允许为任何示例写题材专用判断**。下列“主要验证”全部映射到 v0.1 既有能力（stats/flags/clock/condition/effect/weight/cooldown/once/goto/endings/priority），无需新增引擎功能。

### 1.《我在三线城市给外星人贴手机膜》——荒诞经营模拟器
- 数值：余额、每日客流、外星顾客好评、地球身份暴露度、库存。
- 事件：顾客的手机是正在坍缩的星球；顾客要求贴膜后仍能跨星系通信；隔壁店举报半夜发绿光；外星网红突然探店；进货收到一批只适配四维屏幕的手机膜。
- 主要验证：收入和支出（set/add_stat）、随机经营事件（weight/roll）、条件事件（condition）、数值上下限（min/max 夹紧）、事件冷却（cooldown）。
- 结局（≥4）：成功结局（经营达标）、失败结局（破产）、失败结局（身份暴露）、隐藏结局。

### 2.《在公司厕所偷偷修仙七天》——荒诞限时生存模拟器
- 数值：灵气、精神状态、老板怀疑度、同事好感、剩余厕纸。
- 事件：老板突然在门外开会；同事借纸导致修炼材料不足；马桶出现秘境入口；保洁阿姨识破修仙身份；领导要求提交“飞升周报”；玩家在加班/摸鱼/修炼/隐藏身份之间选择。
- 主要验证：七天时间推进（clock）、一次性事件（once）、条件事件（condition）、事件链（goto）、状态标记（flags）、资源耗尽（compare 到下限）。
- 结局（≥4）：成功结局（飞升）、失败结局（暴露）、失败/中立结局（辞职）、隐藏结局（厕所守护者）。

### 3.《被裁后我开始给鸽子做职业规划》——荒诞人生选择模拟器
- 数值：现金、理智、鸽子就业率、互联网声望、客户投诉。
- 事件：第一位客户坚持想进互联网大厂送信；一只鸽子简历空白但要求月薪三万；鸽子群要求实行双休；自媒体发现并爆红；猎头邀请转型跨物种人力资源；鸽子面试当天集体放鸽子。
- 主要验证：多阶段人生分支（flags + goto）、前置条件（condition）、选项后果（effects）、连锁事件（事件链）、隐藏状态（stats.visible=false 或不展示的 flags）。
- 结局（≥4）：普通结局、失败结局、成功结局、隐藏结局。

三个示例统一要求：可完成至少一轮、至少一个结局可达、无死局、无越界；**每个示例至少含普通/失败/成功/隐藏四种结局**。

## 十二、M0 验收标准

1. 三个手写 GameSpec 全部通过结构校验与引用完整性校验。
2. 引擎对每个示例稳定完成至少一轮核心玩法（开始 → 多回合 → 命中结局）。
3. 自动路径模拟能检测并报告：不可达结局、立即死局、资源越界。
4. 结局可达性：每个示例至少一个结局从初始状态可达（PRD QA-04）。
5. 种子确定性：同 seed 同路径（自动化测试证明）。
6. 浏览器冒烟：首屏加载、开始、选择一次、存档、恢复（PRD QA-05）。
7. 安全：源码与产物不含 `eval`/`Function`/`new Function`/动态执行；无 AI 生成代码进入运行环境。
8. 不调用真实模型、不产生任何模型费用。
9. 类型检查、Lint、生产构建通过。
10. 交付证据包（截图 + 可操作步骤 + 阶段闸门是否表）。
