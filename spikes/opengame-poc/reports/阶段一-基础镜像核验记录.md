# 阶段一 · 基础镜像核验记录（node:20-slim，glibc）

- 时间：2026-10-03
- 用途：修正此前"本地镜像 ID 与官方 manifest 摘要逐字一致（等同官方）"的不严谨表述，把四类摘要分开记账。
- 原则：不重复下载；本轮全部基于**已缓存镜像** + 今晨已记录的官方端点取数 + 本地哈希。

## 1. 四类标识（此前被混用的部分，现分列）

| 概念 | 值 | 含义 |
| --- | --- | --- |
| 官方 linux/arm64 **manifest digest** | `sha256:10fc5f5f33cba34a4befa58fcf95f724e67707fab7c32fb8cd3fcf90ebcc20df` | 官方 `registry-1.docker.io` 对 `20-slim` 索引中 arm64/linux 条目声明的清单摘要（今晨经官方端点取得并记录） |
| 官方 **config digest** | `sha256:6ced300970b1919c3ff96f482c6a342f2bca746922fcdc825e84e3b8f5ab3740` | 上述官方 manifest 内 `config.digest` 字段（今晨经官方端点取得并记录） |
| **本地镜像 ID** | `sha256:10fc5f5f33cba34a4befa58fcf95f724e67707fab7c32fb8cd3fcf90ebcc20df` | 本机为 containerd 映像存储（storage driver=overlayfs/containerd），**镜像 ID 语义即 manifest digest**，不是 config digest |
| **本地 RepoDigests** | `node@sha256:10fc5f5f…`、`docker.m.daocloud.io/library/node@sha256:10fc5f5f…` | 记录该本地内容对应的拉取摘要引用（含缓存来源前缀） |

## 2. 实际拉取来源与过程（如实）

1. dockerd 直连 Docker Hub 鉴权端点三次 TLS 超时（VM 内 fake-IP DNS 与 dockerd 路径不合；宿主 curl 当时可达）。
2. 改经 `docker.m.daocloud.io`（第三方 pull-through 缓存）拉取，**匿名、未登录 Docker Hub**。
3. **按 tag 首次拉取被否决**：与官方当时的 arm64 manifest 摘要不一致（tag 可变 + 缓存旧副本）。
4. 由宿主 curl 匿名 GET 官方 `registry-1.docker.io` 取得 linux/arm64 manifest 摘要 `10fc5f5f…`，**按摘要**经缓存复拉；docker 拉取过程对每个 layer 做 digest 自校验。
5. 本轮（下午）复核：`docker save` 导出已缓存镜像，取其中 config blob 文件并本地 `shasum -a 256`，结果 `6ced3009…`，**与今晨官方 manifest 声明的 config digest 一致**；本地镜像 ID 仍为 `10fc5f5f…`。
6. 本轮复核时官方端点再次不可达（两次 connection reset），故官方侧数值采用今晨已落盘的取数记录；未能当日三测复现官方 GET，如实注明。

**验证链结论**：本地镜像（ID=`10fc5f5f…`）的 manifest 声明 config=`6ced3009…`，本地实际字节哈希=同值 → 本地内容与官方按摘要声明的清单在"manifest 摘要 + config 摘要 + layer 拉取期自校验"三点上闭合。表述采用该验证链，**不再写笼统的"等同官方/逐字一致"**。
